# 导购 H5：实际完成度与下一步

核查基线：`guide-agent` 分支 `894d3a29fc1589836fa7ab7255d85b52236cadf9`（2026-10-13）。以下以代码和离线验证为依据，不沿用旧 Python 工具的完成度，也不把 Coze 项目数据当成本项目效果。

## 产品判断

已有可用的手机 H5 页面和本地工作流骨架，继续在它上面做，不需要另建一套界面。先把 H5 的真实问答、内容和验收做完整，再决定小程序发布。小程序客户端可以复用服务端业务能力，但不是把当前页面换个壳就完成。

导购接待中的三类目标：问顾客条件并选品；直接查参数/服务知识；为已确认商品生成内容。知识问答不以选品或写文案为前提。内容也已有“从商品列表直接确认”的入口，不必先经历推荐筛选。

## 当前有两套运行入口

主线应是 `npm run dev` 的 Next.js H5，服务端在 `app/api/` 和 `lib/guide/`。

`node server/index.mjs` 是早期单文件服务和 `public/` 页面。它仍可用于原规则回归，但**没有新增的知识问答主流程**。此前 README 把它列为主入口，容易让实现和验收错位。本次更新主 README，不删除旧入口。

## 知识资料如何接入

现有 Markdown 保留，新增 `data/knowledge/index.json` 维护文件与范围：

- `file`：对应 Markdown 文件，禁止目录跳转。
- `storeId`、`productIds`：适用门店和商品；空商品列表表示门店通用资料。
- `version`、`claimKey`：资料版本和同一业务规则标识；同规则存在不同有效文本时拒绝确定回答。
- `validFrom`、`validTo`：业务生效/失效日期，格式 `YYYY-MM-DD`。现有演示资料没有提供这些日期，保持 `null` 并显示“未标注”，不编造有效期。
- `reviewStatus`：现有资料均标为 `demo`。真实资料需有来源、负责人审核后再标 `approved`。

答案逐段引用实际文件原文，带文件名、段落、版本和内容哈希。不会联网找其他商品，也不会用模型猜保修年限。当前五条片段上限是工程预算，不是通过评测得出的最佳召回数量。

已知边界：关键词召回对复杂改写和组合问题覆盖有限；长段落可能包含与问题无关内容；目前没有自动文档上传、解析、语义切分、索引增量更新或后台审核界面。真实资料接入前不能将演示条款作为门店承诺。

## 剩余工作优先级

### P0：真实闭环与费用可控

1. 将文字模型接到 **Next.js 实际内容节点**，逐句绑定商品字段/知识片段；保留无依据拒答。模型名称出现在配置中，不代表已获得权限或实际测试成功。
2. 生图先形成服务端预览计划：商品、参考图、模型、尺寸、数量、预计费用上限；导购明确确认后才执行。增加请求幂等、计费未知状态、重复点击保护、成功 URL 到素材卡的完整传递。当前内部授权参数只是适配器防误调用门槛，不是完成的账务/授权系统。
3. 同会话并发请求使用事务/修订号比较，生成期间更换商品时丢弃旧结果。当前 `saveSession` 是最后写入覆盖，不适合多人并发。
4. 统一主线和旧服务，减少两套模型配置、商品规则和页面的长期分叉。

### P1：可用的门店知识问答

1. 收集一小批真实商品表、售后条款和活动规则；先核对版本、有效日期、店铺与 SKU。
2. 先做真实高频问题基线：参数、拆洗、质保、配送、活动冲突、查无资料、商品切换、同义改写。
3. 依据漏检原因再加入语义向量召回、关键词融合与重排，评估召回、回答支持率、拒答和延迟。
4. 做“查资料 → 写内容”的证据复用，资料变化时旧内容失效提示，不仅保留商品 ID。

### P2：多导购试用与发布

服务端登录和门店/导购/顾客权限、知识管理、可靠数据库和文件存储、审计与备份、真实手机和微信浏览器适配。现有演示登录、localStorage 和全量记忆读取不是服务端权限隔离。身份验证前不应作为真实门店对外服务。

## 验收与结果解释

`npm test` 包含原有四组检查，以及新增 Next.js 路由和知识/费用测试；`npm run typecheck` 检查类型。具体执行结果见本次 PR。
